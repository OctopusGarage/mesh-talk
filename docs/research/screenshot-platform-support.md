# Screenshot capture on Windows and Linux

Investigated 2026-10-10. Updated with the shared editor implementation. Native capture still needs runtime validation on Windows and Linux.

## Current contract

`capture_screen(hide_window)` in `src-tauri/src/chat_commands/platform.rs` hides the main window if requested, captures, and restores/focuses it afterward. macOS uses `screencapture` after a Screen Recording permission check; Windows captures the primary display through xcap; Linux asks the Screenshot portal for a screen image. The React caller expects PNG bytes, an empty byte array for user cancellation, or a real error. A successful capture opens the shared selection and annotation editor; sending requires an explicit click. The composer offers “Capture screen” and “Hide window & capture”.

## Platform findings

| Platform | Native route | Important limit for Mesh-Talk |
| --- | --- | --- |
| Windows | `Windows.Graphics.Capture.GraphicsCapturePicker` lets a user pick a display or application window and yields frames that can be encoded as PNG. A desktop app must bind the picker to its owner HWND; support starts with Windows 10 version 1803, and `GraphicsCaptureSession.IsSupported()` should be checked. [Microsoft picker API](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturepicker), [Microsoft capture guide](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) | The picker offers a display/window, not the macOS-style drag-to-select rectangle. Region capture needs an additional selection overlay and crop step. |
| Windows Snipping Tool | The current `ms-screenclip:` protocol has rectangle and window modes and returns a captured file token to the caller. [Microsoft Snipping Tool protocol](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-snipping-tool) | Response delivery requires an **MSIX-packaged app** launched through `Launcher.LaunchUriAsync`; unpackaged Win32 callers cannot receive its `redirect-uri` callback. This repository currently bundles Windows through Tauri's standard Windows targets rather than an explicit MSIX integration (`src-tauri/tauri.conf.json`). Do not rely on this protocol for the current installer. Clipboard polling would be an unreliable substitute because it cannot distinguish the user's prior clipboard image from the requested capture. |
| Linux, Wayland | `org.freedesktop.portal.Screenshot` returns a URI for the result. Interface version 2 adds an `interactive` hint; version 3 adds `AvailableTargets` and a specific `target`, including user-selected window and area. [XDG Screenshot portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Screenshot.html) | `interactive` is only a hint. Area/window availability must be read at runtime from the installed portal and backend; a version 3 specification does **not** mean every distribution or desktop offers region selection. Respect the portal's user consent UI. Request response `1` means cancellation, distinct from other failure. [XDG Request interface](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html) |
| Linux, X11 | A capture library can read a monitor or window and crop a chosen region. [xcap project API and platform matrix](https://github.com/nashaofu/xcap) | Such libraries supply image pixels, not an interactive region selector; Mesh-Talk would need its own overlay. This route does not generalize to Wayland. |

The Rust `ashpd` crate exposes the portal screenshot request builder, including `interactive` and `target`, so a Linux portal implementation can avoid handwritten D-Bus glue. [ashpd screenshot API](https://docs.rs/ashpd/latest/ashpd/desktop/screenshot/struct.ScreenshotRequest.html) The `xcap` project advertises Windows, X11, and Wayland capture, but its own feature matrix marks Wayland capture as limited in some scenarios; its README lists additional Linux build dependencies including XCB, D-Bus, PipeWire, Wayland, and EGL. [xcap README](https://github.com/nashaofu/xcap) The repository's current Linux CI/release package lists (`.github/workflows/ci.yml`, `.github/workflows/release.yml`) do not install that full set.

## Recommendation

The implemented interaction has the same decision points on all three platforms: select a region, annotate with pen/rectangle/arrow/text, then send or cancel. Capturing alone never sends the desktop. macOS uses its native desktop region selector and opens the editor with that area already selected. Windows and Linux capture a screen image, then use the shared editor's drag selector. The editor appears inside the Mesh-Talk window with a static image of the display, rather than as a transparent overlay across the live desktop. On Windows and Linux the window expands to fullscreen while editing, then returns to its prior size. Windows currently captures the primary display. Linux relies on a working desktop Screenshot portal and may show the system's picker or consent UI before the editor; it requests a screen target when portal v3 advertises one. Older portal versions use the interactive hint. Sessions without a working portal report an error. X11 without a portal does not yet have a separate capture backend.

The implementation retains both composer modes and the existing image-send pipeline. The composer disables screenshot capture when the current Windows display or Linux portal cannot provide a screen image; macOS keeps it available so the OS permission prompt can be requested. A future native overlay could provide selection over the live desktop and a display picker for multi-monitor setups; that requires platform-specific window management beyond the shared editor.

## Validation required before shipping

1. Unit-test PNG/empty/error mapping, portal version and target decisions, and restore-on-cancel/error behavior.
2. Run native interactive checks on Windows 10/11 with the actual distributed installer: region/window selection, Escape, app hidden/visible, multiple displays with mixed DPI, and capture errors.
3. Run native checks on Linux X11 and at least GNOME Wayland and KDE Wayland: available targets, consent dialog, cancellation, screen/window/area paths, portal absent/old, and multiple displays/scaling. A virtual X11 CI session does not prove Wayland behavior.
4. Add all needed Linux native build packages to CI/release jobs before choosing a library that requires them, then run the project health gate and a real send-to-recipient smoke test on each platform.
