# Routed-network discovery research for Mesh Talk

Historical research and design options recorded before this branch's implementation. For current behavior, supported topologies, and tested limits, see [routed network discovery](routed-network-discovery.md) and [network topologies](network-topologies.md). Recommendations below are research notes, not claims that every option was implemented.

Research date: 2026-10-14. Sources are Tailscale's own documentation, WebRTC specifications and IETF protocol specifications. This note separates documented behavior from design inferences. Users install and connect Tailscale independently. Mesh Talk detects an already-running client for automatic peer discovery, without requiring Tailscale for ordinary LAN use.

## Baseline at research time

At research time, Mesh Talk used a signed, custom UDP multicast announcement on `224.0.0.167:47474`, with unicast replies and a scan of each local IPv4 `/24`. It did **not** use mDNS. Its data path was a Noise-encrypted TCP connection; the post office stored encrypted events for offline delivery. See [architecture §4](ARCHITECTURE.md) and [`discovery/service.rs`](../crates/mesh-talk-core/src/discovery/service.rs).

## Recommended integration

1. **Keep LAN discovery automatic.** Continue signed multicast, unicast replies and local scan; optionally add standard LAN DNS-SD later. mDNS is link-local, so it does not provide first contact across an ordinary routed VPN. See [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) and [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
2. **Automatically enumerate an existing tailnet as an optional discovery source.** If an installed Tailscale client is running and its local peer inventory is accessible, read visible peer IPs, then send bounded unicast UDP probes to the existing discovery port. The receiver verifies Mesh Talk's signed announce before adding a peer. The adapter must never launch, install, log in to, or reconfigure Tailscale. It runs in the desktop/host layer, not core. The first adapter may use the documented CLI; a LocalAPI implementation is optional only after its access and compatibility are validated per platform. Neither MagicDNS nor interface inspection enumerates tailnet members. See [Tailscale CLI](https://tailscale.com/docs/reference/tailscale-cli) and [MagicDNS](https://tailscale.com/docs/features/magicdns).
3. **Keep provider-neutral bootstrap paths.** If client inventory is unavailable, a user can enter or scan an IP address, IPv6 address, DNS hostname or application invitation carrying the Mesh Talk identity fingerprint. After one authenticated cross-network connection, authorized peers can exchange bounded signed identity proofs and untrusted route hints, then discover further peers automatically. A separate routed network cannot support zero-touch first contact without some candidate source, seed, or shared directory: there is no destination for the first packet. This is a network-level inference from [mDNS's local-link scope](https://www.rfc-editor.org/rfc/rfc6762), not a Tailscale-specific limitation.
4. **Keep route selection separate from identity.** A peer may have local and routed addresses plus manually supplied hostnames. Authenticate each route's response, deduplicate by Mesh Talk device identity, and retry routes with measured reachability. Retain several endpoint candidates per device instead of replacing `PeerRecord.addr` on each announcement. Do not infer trust from an IP address, including one in Tailscale's `100.64.0.0/10` range: addresses are network-scoped and can be reassigned. Network reachability is separate from Mesh Talk account/device authorization. See [IP assignment](https://tailscale.com/docs/concepts/ip-and-dns-addresses) and [device visibility](https://tailscale.com/docs/concepts/device-visibility).
5. **Keep TCP for chat and files in the first release; retain WebRTC for existing calls.** QUIC is a secure multiplexed UDP transport, but it would require a new Mesh Talk listener, framing and session behavior, plus migration testing. WebRTC data channels use SCTP over DTLS over ICE/UDP and add signaling and a different stack. Mesh Talk should use any IP path made available by the OS; when users choose Tailscale, its network stack handles NAT traversal and relay fallback. Add QUIC only for an observed transfer/concurrency need. The protocol descriptions follow [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) and [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html); the recommendation is an inference from those specifications and [Tailscale connection types](https://tailscale.com/docs/reference/connection-types).

## Refined module design

- **Discovery source seam:** A source emits endpoint *candidates* or observations, never trusted peers. LAN is a continuous event source; Tailscale inventory is a snapshot; manual seeds and authenticated peer hints are stored or received asynchronously. An `async fn discover() -> Vec<Candidate>` alone would force LAN listening into a polling shape. A small common sink/event interface, or a discovery coordinator, should normalize them. The core accepts generic endpoint candidates. The optional Tailscale adapter stays in the desktop/host layer and has no effect when Tailscale is absent.
- **Verified peer and routes:** Keep the stable device public identity, verified account binding, and a bounded set of routes. Each route carries an address or hostname, origin, last authentication time, recent success/failure and expiry. Do not encode DERP or Tailscale peer-relay as Mesh Talk route variants. A verified UDP announcement supplies an identity proof and a route candidate; a pinned Noise handshake confirms the endpoint before sensitive use. The existing encrypted historical route cache stores one IP per identity, so its migration is part of this change.
- **Route choice:** Start with recent authenticated success, short connection timeout, fallback, exponential backoff and hysteresis. Measure connection/handshake RTT and failure rate passively. Avoid a fixed `LAN > Tailscale > manual` rule and avoid arbitrary 0–100 scores, continuous bandwidth probes, and treating transport failures as lost identities. Later add active probes only if field measurements show a need. Keep ephemeral reachability separate from durable identity/account proof and user permission.
- **Privacy:** Automatic Tailscale probes, other unicast probes and peer-hint sharing respect the existing visibility gate and application permissions. Rate-limit and cap candidate lists; exchange only hints for peers the recipient is allowed to learn about. A peer hint or reachable IP does not create an account grant or online presence; a manually pinned contact must still pass application authorization.
- **Calls:** Keep authenticated Mesh Talk signaling, but test actual ICE gathering and selected candidate pairs on macOS, Windows and Linux webviews. Standard `RTCPeerConnection.addIceCandidate()` adds a *remote* candidate; it cannot force a local Tailscale host candidate. Do not synthesize one by editing SDP. If a webview omits the Tailscale interface or cross-site ICE fails, evaluate an explicit TURN service reachable over the tailnet or a native media stack. This is distinct from Tailscale's transport relays. See [WebRTC specification](https://www.w3.org/TR/webrtc/#dom-peerconnection-addicecandidate) and [WebRTC ICE guidance](https://webrtc.org/getting-started/peer-connections).

## Validation scenarios

- Two hosts on distinct LANs with Tailscale already connected by the users: detect accessible peer inventory automatically, unicast probe, verify signed identities, then exchange Noise/TCP chat and files through the selected IP path, without a Mesh Talk setup step.
- Tailscale absent, disconnected, or inaccessible from the packaged app: LAN still works and the optional adapter degrades to manual or other provider-neutral seeds.
- A remote network with no accessible peer inventory, seed or rendezvous: show the actionable first-contact requirement rather than claiming automatic discovery. A blocked UDP probe should still allow a manually seeded TCP handshake when TCP is reachable.
- A DERP or peer relay path: verify app behavior without assuming Tailscale direct connectivity; inspect `tailscale status`/`tailscale ping` to classify the outer path ([connection types](https://tailscale.com/docs/reference/connection-types)).
- Tailnet client unavailable, IP changed, MagicDNS rename, overlapping home/office RFC1918 ranges, and a subnet-routed host: confirm route refresh and identity pinning while LAN discovery and offline post-office delivery remain functional.

## Implementation questions to validate

- Validate how to read existing-client peer inventory from each packaged desktop app. The CLI is documented across desktop platforms but its JSON may change; the LocalAPI has platform-specific access details. Neither may become a startup or runtime dependency of core, and no Tailscale setup belongs in Mesh Talk.
- Test macOS sandboxed Tailscale variants and Windows/Linux interface binding behavior in actual installations; the cited platform docs establish Tailscale connectivity, not that Mesh Talk's existing socket bindings work on every variant.
- Measure cross-site call ICE candidates and selected pairs before promising a call fallback or choosing between TURN and native media.
